# Cycle 15 setup — what it takes to run pmx on this system

**Eight diagnostic rounds established the following. Recorded so it is not rediscovered.**

Cycle 15 asks a different question from Cycle 14: not "what is the ΔΔG of the peptide"
but "which pocket residues drive δ/μ discrimination". It mutates the *receptor*
(W284→K, the δ/μ-divergent position with the largest chemical change) rather than
decoupling the peptide twice, so the ~2350 kJ/mol absolute that destroyed Cycle 14's
precision is never formed.

## The six obstacles, in order

**1 · pmx is not installed and not on PyPI.**
`pip install pmx` fails — no distribution of that name. Install from source:
```
pip install --user "git+https://github.com/deGrootLab/pmx.git@develop"
```
Compute nodes do reach PyPI and GitHub (HTTP 200 in <0.3 s), so this works from a job.

**2 · It installs against the shared Anaconda, not the project env.**
`source $D/envs/gmxcuda/bin/activate` fails silently and pip falls back to
`/srv/ss/sib/ibu/rocky8/2023072800/software/Anaconda3/2022.05/bin/python3`.
**Every later step must call that interpreter explicitly** or the import vanishes.

**3 · `python -m pmx` does not work.** The package has no `__main__`. There is a CLI at
`~/.local/bin/pmx` but its `mutate` subcommand prompts for the force field interactively
and consumes piped stdin in an order that is easy to get wrong. Use the API:
```python
from pmx.alchemy import mutate
mutate(m=Model(pdb), mut_resid=284, mut_resname='LYS', ff='amber14sbmut', mut_chain='A')
```

**4 · The force field must be found via GMXLIB.**
`get_ff_path` searches `$GMXLIB` and `$GMXDATA/top` only — it does not look inside its own
package. Set:
```
export GMXLIB=<site-packages>/pmx/data/mutff
```

**5 · The system is AMBER ff14SB, NOT CHARMM.**
This matters more than anything else here. The topology is a **standalone ParmEd file with
zero `#include` lines**, so the force field is not stated anywhere and must be inferred:

| evidence | reading |
|---|---|
| atom types `CX`, `2C`, `3C`, `HP`, `C*`, `CW`, `NA` | ff14SB-specific |
| `fudgeQQ = 0.83333` (5/6) | AMBER 1-4 scaling; CHARMM uses 1.0 |
| water named `WAT` | AMBER convention |
| header: generated by ParmEd from a `gmxmmpbsa` env | Amber-side setup |

Use `amber14sbmut.ff`. **Using `charmm36m-mut` on this system would not raise an error** —
it builds, minimises, samples and returns a free energy with a tidy error bar. The number
would be meaningless, because one residue would carry parameters from a different force
field than the other 368. No gate in the pre-registration can detect this.

**6 · Hydrogen naming: pmx wants HB1/HB2, the system has HB2/HB3.**
The PDB v3 versus legacy AMBER split. `Model(..., rename_atoms=True)` does **not** fix it.
The failure surfaces as an opaque `IndexError: list index out of range` deep in
`_set_conformation`; instrument `pmx.molecule.Molecule.__getitem__` to get the real name.
Rename within the target residue only:
```
HB2 -> HB1 ,  HB3 -> HB2
```

## Still open

The protein must be spliced back into the solvated system and re-equilibrated. Because the
topology is standalone ParmEd with no includes, the protein `moleculetype` has to be
replaced rather than re-included, and that step is not yet validated.

## Validation that must not be skipped

The build asserts the hybrid residue carries **both** side chains — TRP ring atoms
(`CZ2 CH2 NE1 CE2 CD1`) *and* the LYS/dummy atoms. A single-topology result that looks like
a plain lysine would run perfectly and measure nothing.
